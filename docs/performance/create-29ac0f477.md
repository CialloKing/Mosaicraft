# 一次 `create` 的性能验收（基线 `29ac0f477`）

Windows Release，Ryzen 9 7940H、RTX 4060 Laptop (8188 MiB)。本机原始日志和保存的二进制位于 `build/perf-create-29ac0f477/`；仓库内的[配对样本与画质数据](create-29ac0f477.json)含二进制、目标和快照指纹。每个 `create` 在同一份 45,613 行的隔离数据库的**新副本**上运行，固定种子 42、Top-10、9×16 输出图块、实际写入 PNG。计时从创建 CLI 进程到其退出，不开逐候选诊断，不含数据库备份和事后哈希。与固定排列的原生输出、Web UI 连续任务、建库结果分别报告。Deep Zoom 不参与计时。

## 单次生成：相对原版的真实墙钟

两轮预热、八轮顺序交错的配对，自动线程。A 为保留现有图库格式的读取/校验/提交优化；P1 为 CPU `fast` 特征复用。下表为**组合构建实测**，不是把单项加速相加。列中是进程墙钟中位数（秒），括号是逐对“新版/原版”比值中位数的 bootstrap 95% 区间。不同窗口的绝对秒数受频率、热状态等影响，不跨表比较。

| 格数 × 候选 | CPU 原版 → P1+A | CUDA 原版 → P1+A |
|---|---:|---:|
| 900 × 150 | 2.176 → 1.770（0.798–0.844） | 2.310 → 1.972（0.783–0.909） |
| 3,600 × 150 | 2.832 → 2.251（0.793–0.843） | 2.802 → 2.330（0.814–0.859） |
| 57,600 × 150 | 10.779 → 9.342（0.865–0.887） | 7.862 → 7.348（0.930–0.951） |
| 14,400 × 600 | 6.157 → 5.322（0.850–0.898） | 4.759 → 4.472（0.895–0.938） |

单项对照（同规模顺序）：A 单独的 CPU 配对比为 **0.820 / 0.836 / 0.961 / 0.935**，CUDA 为 **0.852 / 0.865 / 0.944 / 0.922**，八个区间上界都低于 1。P1 单独的自动线程 24 对结果见 `p1-auto24`：重负载 15.511 → 14.600 s；900 格区间跨 1，不声称小任务的 P1 加速。保留旧格式，无需重建、无新磁盘副本要求；B 权威特征包尚未验收。

**画质：**组合对照每个后端六类目标 × Top-1/10 × 三种子，原版和新版均为 `fast`。CPU 与 CUDA 各 12/12 组通过逐种子 FP64 均值、P90、P99、覆盖率、半径 3 重复和独立素材检查。CPU 四组计时样本 PNG 完全相同。CUDA 在 57,600 格不保证逐像素重复：A 单独八个正式候选样本有三种哈希（4/2/2），组合也出现了变化。无样本从耗时区间剔除；小规模画质门槛通过不等于大图像素一致。

## 独立场景与取舍

| 比较 | 工作量 | 原版 → 候选中位数 | 结论 |
|---|---|---:|---|
| CUDA 原始目标上传、CPU Canny | 57,600 × 150 | 12.632 → 13.835 s | 上传 9,953,280,000 → 24,883,200 B，却更慢（1.061–1.223）；保留旧 CUDA 路径 |
| 便携 HTML 有界导出 | 相同排列 320 格，180×320，8 线程 | 2.702 → 1.516 s | 保留；清单、输出大小一致，工程检查通过 |
| 流式 PNG / JPEG 重叠编码 | 同一原生排列 | PNG 1.896 → 1.859；JPEG 0.845 → 0.853 s | 区间跨 1，未默认启用；无压缩 TIFF 为对照，不计为提速 |
| 仅流式 PNG 固定 Sub | 同一原生排列、关闭重叠 | 1.575 → 1.335 s | 解码像素一致；28,907,550 → 30,889,564 B（+6.9%），速度不等于无代价 |
| CPU 建库仅并行哈希 | 建 272 张 / 追加 80 张，含重复输入 | 建库 1.260 → 1.107；追加 0.561 → 0.471 s | 身份、特征及行数一致；追加区间上界 1.132，未达默认准入 |
| 在并行哈希之上双缓冲 | 同上 | 建库 1.306 → 1.456；追加 0.522 → 0.643 s | 均显著更慢；不默认启用 |

ANN 直接写批次在 CPU、8 线程、八对的四个区间均跨 1，不能据此宣称提速。模板设备 Canny 的早期组合探索仅有两对，不能代替内核特化后的独立验收。Vulkan、Metal、不同 GPU 架构、常驻 GPU 图库均无本轮速度承诺。

## 复核

- `scripts/benchmark_create.py`：用保存的 `baseline`、`layout-a`、`p1` 或 `combo` 中的 CLI 和 `build/backend-retest-20261118/runs` 重放。`--extend` 检查输入和二进制指纹，不用新二进制重标历史数据。
- `scripts/precision_quality_gate.py --baseline-match ...`：逐种子比较同后端的两个 `fast`；与旧 `compatible` 的比较不代替此门槛。
- `scripts/benchmark_render.py`、`scripts/benchmark_library_build.py`、`scripts/benchmark_hot_jobs.py`：固定排列、独立新建/追加、同进程连续正式任务分别测量。不要同时运行性能测试。GPU 事件、异步等待与 CPU 的时间可能重叠，不相加作为墙钟。

### CPU 连续任务和建库追加补测

- 在相同 P1+A 上只开关同进程缓存。每个会话有独立数据库和历史，计时从提交任务到轮询确认最终输出；会话值为十次任务墙钟之和，不含启动服务器或任务间的校验。两轮预热、八对会话：首次 **1.438 → 1.469 s**（1.011–1.032），第二次 **1.339 → 1.197 s**（0.862–0.909），十次 **16.151 → 14.596 s**（0.884–0.920）。正式候选的八次首次均无命中，之后 72 次均复用索引和 45,613 行；每次数据库提交增加 900 格，与对照同位置的 PNG 一致。缓存占用不是免费的，一次性 CLI 没有这项收益。
- 并行哈希保留原八对补到 24 对。新建 **1.157 → 1.080 s**（0.870–0.978），追加 **0.498 → 0.468 s**（0.804–1.066）。仅对 CPU 新建图库启用；不改变追加、同目录输入、模板或通用 CUDA 的默认行为。双缓冲未启用。

### 对照实验的最终取舍

以下均为**同一测量窗口内**的新旧配对。实验构建不是发布默认值；不能把各表的秒数相加。

| 仅改变的一项 | 场景、配对数 | 对照 → 实验（秒） | 配对比 95% 区间；决定 |
|---|---|---:|---|
| CPU LBP（标量 → SIMD） | 57,600 × 150；8 | 11.673 → 10.978 | 0.916–0.973；保留 |
| ANN 结果直接写入批次 | 900 / 3,600 / 57,600 / 14,400 格；各 24 | 1.846 → 1.815 / 2.423 → 2.436 / 11.683 → 11.566 / 5.590 → 5.608 | 四个区间均跨 1；不启用 |
| 共享线程池并预取下一批 | CPU，8 线程，57,600 × 150；8 | 10.435 → 10.719 | 1.006–1.055；不启用。单线程共用工作池，不预取 |
| 模板 CUDA 原始目标 + 特化设备 Canny | 8 线程，57,600 × 150 / 14,400 × 600；各 8 | 8.655 → 7.451 / 5.108 → 4.691 | 0.844–0.901 / 0.889–0.967；重负载有收益，未完成独立全画质验收，且小图短测未显示收益，不启用 |
| 非模板 CUDA 直接上传 | **272 张、91×163** 独立图库，900 / 57,600 格；各 8 | 0.385 → 0.476 / 3.418 → 3.133 | 1.146–1.308 / 0.900–0.938；小图回退，保留旧默认，两组 PNG 均相同 |
| CUDA Web UI 会话：首次 / 第二次 / 十次总计 | 每次 900 格，8 对会话 | 1.440 → 1.456 / 1.437 → 1.362 / 15.189 → 14.738 | 0.972–1.018 / 0.915–1.021 / 0.929–0.994；十次有收益，单次不能断言。模板 CUDA 只复用 ANN，不常驻 GPU 图库 |

在同一 P1+A 二进制筛选线程上限，重负载相对自动线程的配对比（每项仅 2 对）：CPU `1/4/8/16` 分别为 `4.92/1.61/1.09/0.99`，CUDA 为 `3.41/1.40/1.17/1.06`。没有证据修改自动后端或线程选择。不为无显著收益的试验再增加轮数。

固定排列 `render --benchmark` 的 `decodeWorkerMs`、`resizeWorkerMs` 只统计实际加载图像的工作线程；它们与放置时间重叠。`codecWriteMs` 是行编码写调用的子区间，不是编码总时间；没有调用行写入的模式请看 `encodingMs`。同一 320 格排列，以 8 线程流式 PNG 复核：原生 2880×6400 的缩放为 0 ms；1440×3200 缩放为 8.25 ms，两者各解码 320 次，均与旧版对应尺寸解码后的像素一致。这里是单次诊断，不是性能配对。

## 生产默认构建的快速复核

以 `1940ece61` 的源码恢复 CMake 生产默认值后，在 Windows 重新构建 CPU 和 CUDA+Vulkan Release，各运行一次 CTest，两者都通过 **10/10**。下面的真实 CLI 墙钟统一来自同一份 CUDA+Vulkan 可执行文件，分别强制 CPU 和 CUDA；建库和会话收益不混入。每组 **1 次预热、3 对交错测量**，不报置信区间、不用短测替代上文的八对/二十四对准入。`final-cpu`、`final-cuda` 中保留每一对和输出哈希。

| 默认线程，150 候选 | 基线 → 本次默认（秒，中位数） | 逐对耗时比的中位数 | 新版较快 |
|---|---:|---:|---:|
| CPU，900 格 | 2.333 → 1.849 | 0.803 | 3/3 |
| CPU，57,600 格 | 11.696 → 10.243 | 0.876 | 3/3 |
| CUDA，900 格 | 2.419 → 2.027 | 0.838 | 3/3 |
| CUDA，57,600 格 | 8.052 → 7.522 | 0.952 | 2/3 |

CUDA 大图第三对为 **8.178 → 8.292 s**，未排除。四组本次短测的输出哈希分别在各自组内一致，不覆盖前面已记录的 CUDA 同种子分歧。最终 `fast` 另以锐利边缘（Top-1、种子 42）和素材稀缺（Top-10、种子 20261111）在 CPU、CUDA 回放，4/4 的完整选图索引、匹配数和缺失数均与已通过六类画质验收的 P1+A 构建一致。没有把这四次回放表述为最终构建重跑了全画质矩阵。

独立单次诊断（57,600 格，**不计入墙钟样本**）：CPU / CUDA 的图库打开与校验分别为 256 / 271 ms，读取并校验记录 336 / 379 ms，ANN 加载 236 / 257 ms，目标特征阶段 3.356 / 2.680 s。采样到的进程 RSS 峰值约 248 / 362 MiB；CUDA 设备总显存采样峰值约 2.28 GiB，进程级显存不可用，不能把前者记成项目独占。默认模板 CUDA 的目标特征上传仍为 9,953,280,000 B，事件上传/计算/下载 796 / 1077 / 37 ms，主机等待 469 ms；这些区间会重叠，不能相加。另一次性的**图库**上传仅 17.2 ms，设备图库 95,148,718 B；只看这笔传输，不足以证明长期占用显存值得。GPU 常驻与按任务加载的独立会话 A/B 尚未实施。

同样用 1 次预热、3 对测量单独筛查模板设备 Canny 的小任务：对照是 P1+A 而不是原版，900 格、自动线程 **2.097 → 2.189 s**，3 对中 2 对较慢，输出哈希相同。这个样本不能证明稳定回退，也不能证明没有小图代价。重负载的八对收益仍然有效，但不足以全局启用；未继续扩测。

**未完成而非无收益：**没有实施 P5-B 权威特征包与跨文件追加恢复的对照，因此不主张 A 一定快于 B，也不改变图库契约或要求重建。未测 macOS Metal 性能；Deep Zoom 未纳入测速或优化。
