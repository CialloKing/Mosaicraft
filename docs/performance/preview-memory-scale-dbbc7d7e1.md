# Windows CPU 预览：更大内存上限对照

对照为 `main@dbbc7d7e1` 的实际自动策略。同一 Windows x64 CPU Release 基准二进制（`526cd2273`），只用试验环境变量改变缓存上限。各档都使用原有并行特征源校验；不改筛选、评分、线程或默认策略。使用 45,613 张素材的私有快照、`target3.jpg`、`fast`、9×16 匹配块、种子 42、自动线程。API 墙钟从提交到收到完成结果，不含服务启动、浏览器绘制和推荐读取。“冷首轮”指新进程首次预览，不清空系统文件缓存。

## 57,600 格 × 600 候选

这个负载超出当前自动扩容范围，实际使用 **128/64/64 MiB**，三类对象都装不下。大档为 **1024/256/384 MiB**（依次为评分、目标特征、ANN 候选，合计上限 1664 MiB）。正式运行只测冷首轮和随后的 Top-N 10→5，2 次预热、8 对交错，诊断关闭。

| 操作 | 当前自动中位 (秒) | 大档中位 (秒) | 配对耗时降幅 | 耗时比 95% 区间 |
| --- | ---: | ---: | ---: | ---: |
| 冷首轮 | 23.570 | 18.898 | 20.2% | 0.775–0.839 |
| 只改 Top-N | 26.272 | 12.792 | 51.0% | 0.477–0.501 |

两步合计配对中位耗时下降 **36.8%**（比值 95% 区间 0.628–0.654）。各轮选图摘要一致。

另一次 1 次预热、3 对初筛，改 Lab 权重（0.20→0.50）和随后再改 Top-N（5→8）的中位墙钟分别为 **26.976→12.796 秒**和 **26.915→14.000 秒**；这是初筛，不混入正式样本。

单次诊断拆分了档位，运行后另读参考 JPEG 和三个位置的推荐：

| 评分 / 特征 / ANN 上限 (MiB) | 首轮预约 (MiB) | 改权重时的预约 (MiB) | 进程峰值工作集 (MiB) | 改权重 (秒) |
| --- | ---: | ---: | ---: | ---: |
| 128 / 64 / 64（自动） | 0.0 | 0.0 | 301.2 | 28.712 |
| 512 / 128 / 64 | 556.0 | 556.0 | 837.8 | 24.719 |
| 512 / 128 / 192 | 687.9 | 687.9 | 968.4 | 19.172 |
| 1024 / 256 / 384 | 687.9 | 1129.7 | 1397.5 | 14.942 |

- 一张评分表 **441.8 MiB**，目标特征 **114.3 MiB**，独立 ANN 候选 **131.8 MiB**。只改 Top-N 时，512 MiB 的评分上限已经能命中，评分表自身就包含候选；不必另留 ANN 候选。命中仍要做邻域惩罚和随机重选；不会省掉整个匹配阶段。
- 改权重时，512/128 档已经命中目标特征；把独立 ANN 上限从 64 提至 192 MiB 后，`annQueryMs` 在这次诊断由 **5513→158 ms**。1024 MiB 评分上限则能在旧预览尚持有旧表时保留新表；权重变化仍要重新评分。权重后再改 Top-N 时大档确实命中评分表，但单次诊断未证明它比 `512/128/192` 的重算更快。
- 冷轮没有缓存命中。保留评分表会走现有的按需生成推荐路径，因此冷轮墙钟差异不能解释为复用计算；正式计时不含以后按需读取推荐。

## 57,600 格 × 150 候选：原场景

当前自动为 **256/128/64 MiB**，试验只提高评分上限至 **512 MiB**。1 次预热、3 对初筛：冷首轮 **14.022→13.511 秒**、只改 Top-N **9.202→9.411 秒**，两者没有可靠收益；改权重 **12.406→10.551 秒**，再改 Top-N **11.020→9.816 秒**，有加速迹象。四步合计的配对中位耗时降幅约 **8.2%**，未做正式复验。

单次诊断中原档和两种实验档的首轮都只预约 **292.4 MiB**。改权重时旧评分表仍在，原档不能同时保留两份 145.2 MiB 的评分表；试验档可保留，瞬时预约 **437.5 MiB**。服务峰值工作集由约 **565 MiB** 增到 **697 MiB**。合计上限再从 704 提至 1664 MiB 没有改变该场景的缓存占用和命中，没有继续加内存的依据。

## 102,400 格 × 150 候选：更大的网格

这是单次诊断，不作正式速度结论。目标特征实际占 **203.1 MiB**，原档和 128 MiB 特征试验档都放不下，256 MiB 试验档可保留。与 `512/128/192` 直接对照，改权重时 `featureMs` **6099→22 ms**，API 墙钟 **20.605→13.367 秒**；服务峰值工作集约 **793→985 MiB**。独立 ANN 候选只占 **58.6 MiB**，原有 64 MiB 就够。这里需要更大的是目标特征缓存，不是 ANN。

## 验证、决策与复现

所有对照内逐格素材 ID 摘要一致。独立诊断的参考 JPEG 和三个位置推荐的 ID/顺序也一致；未逐格验证内部候选距离，不外推到 CUDA 或其他平台。Windows CPU Release 核心测试通过，私有快照的 SHA-256 前后一致，不写真实图库。工作集是各诊断进程的生命周期峰值，包括计算与诊断所用内存，不等于三项预约的总和。

**维持默认不变。** 已经命中的场景继续提高上限不会加速。若继续做自动策略，按实际对象大小和占用版本数设上限：大量候选只调 Top-N 先验证 `512/128/64`；频繁改权重先验证 `512/128/192`，再衡量是否值得留两份评分表；格数增加时优先评估目标特征，而非统一放大。中间档和大网格都未完成正式对照，不据此设新默认。

```powershell
$exe = 'build/windows-cpu/Release/bin/MosaicraftWebUI.exe'
python scripts/benchmark_preview.py --baseline $exe --candidate $exe `
  --prepared build/backend-retest-20261118/runs --input test_input_photos/target3.jpg `
  --output build/preview-memory-scale-replay --baseline-mode auto `
  --variants 1024-256-384+stamps --candidates 600 --steps cold top --rounds 8 --warmups 2
```

对照中间档加入 `512-128-64+stamps`、`512-128-192+stamps`；测大网格用 `--tiles 102400`，移除 `--candidates 600`。单独采集诊断用 `--diagnose --verify-artifacts --rounds 1 --warmups 0`。见[机器可读数据](preview-memory-scale-dbbc7d7e1.json)，未压缩原始日志位于 `build/preview-memory-scale/`。
