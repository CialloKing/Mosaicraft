# 第二轮有界匹配验收

测量日期：2026-10-13。版本保持 **1.14.2**，特征版本保持 **v6**，HTTP API 合约保持 **2.0**。没有发布 Release。实现包含紧凑选择结果、任务内特征读取会话、批次匹配及工作区复用，计算实现提交为 `d1f1555`。

## 预算与实现范围

| 项目 | 较小预算对照 | 默认预算 |
|---|---:|---:|
| 主机匹配缓冲 | 64 MiB | 256 MiB |
| CPU 特征缓存载荷 | 64 MiB | 256 MiB |
| 每批最多小块 | 256 | 1024 |
| CUDA 评分临时显存 | 256 MiB 及可用显存检查 | 同左 |

按需分配并复用容量，不预先占满预算。批次根据 RGB/特征尺寸、ANN 查询、候选及评分数组和候选去重临时数组计算；CPU 大库还根据候选缓存容量缩小批次。单块超过预算时独占一批。末批只处理有效元素。CUDA 内部沿用原有 256 张特征提取粒度并复用输入暂存，外层仍按较大批次统一完成 ANN、评分和顺序选图。

CUDA 预算能容纳两套缓冲时，用一个任务内协调线程提前准备下一批目标特征和 ANN，与当前批 CPU 选图重叠。两套缓冲的容量都计入主机预算；64 MiB 对照场景容不下两套暂存时采用串行流程。准备仍复用最多 8 个线程的现有池，邻域惩罚、排序、随机选择及状态更新都留在原选图线程。

CPU 会话顺序预载可容纳的完整有效包，并在首次使用记录前校验版本、图片摘要和来源属性；不适合预载时采用按需读取及 LRU。损坏包、旧 v2 包及缺失源特征保留第一轮回退和评分惩罚。来源在任务内首次使用时校验，读取会话不作为持续监控源文件变化的机制。

邻域窗口、最近使用位置、Grid 去重和随机数状态跨批次保留。每块仅保存图库索引，分析持有标量及最差 20 块的详细特征。ANN、线程池、特征/评分工作区和缓存在贴图前释放；关闭分析时释放目标图。

上述预算不是 RSS 上限。完整目标图、图库记录、ANN、缓存元数据及 LRU 节点、OpenCV/CUDA 工作区、图片缓存和输出缓冲另占内存；CUDA 图库仍完整上传。目标解码和 PNG 编码策略未改变。

## 性能结果

五个场景的总耗时变化都在 5% 回退上限内。CUDA 大样本中，预算内预取使匹配墙钟中位数从小预算的 37.616 s 降至 24.093 s；主进程峰值增加约 50.5 MiB，整体耗时降低 33.3%。原始 60 次运行、二进制/输入摘要、阶段和缓存计数见 [JSON 记录](performance/phase2.json)。

| 场景 | 基线中位数 | 默认预算中位数 | 相对基线变化 | 基线 / 默认峰值内存 |
|---|---:|---:|---:|---:|
| CPU JPG，batch，1,600 块 | 4.095 s | 3.844 s | -6.1% | 483.3 / 477.6 MiB |
| CUDA JPG，batch，1,600 块 | 3.709 s | 3.689 s | -0.5% | 586.0 / 580.9 MiB |
| CUDA PNG，stream，1,600 块 | 8.812 s | 8.846 s | +0.4% | 274.8 / 344.4 MiB |
| CPU PNG，stream，160,000 块 | 58.131 s | 59.065 s | +1.6% | 874.2 / 287.5 MiB |
| CUDA PNG，stream，160,000 块 | 43.800 s | 33.168 s | -24.3% | 1079.3 / 415.6 MiB |

| 场景 | 小预算中位数 | 默认预算中位数 | 默认相对小预算变化 | 小预算 / 默认匹配缓冲峰值 |
|---|---:|---:|---:|---:|
| CPU JPG，1,600 块 | 4.210 s | 3.844 s | -8.7% | 0.89 / 3.50 MiB |
| CUDA JPG，1,600 块 | 3.737 s | 3.689 s | -1.3% | 43.35 / 91.59 MiB |
| CUDA PNG，1,600 块 | 8.361 s | 8.846 s | +5.8% | 43.35 / 91.59 MiB |
| CPU PNG，160,000 块 | 59.849 s | 59.065 s | -1.3% | 0.87 / 3.44 MiB |
| CUDA PNG，160,000 块 | 49.760 s | 33.168 s | -33.3% | 43.35 / 93.61 MiB |

大样本默认 157 批、小预算 625 批。匹配缓冲峰值包含实际容量、候选去重临时数组和排序工作区；CUDA 预取的两套缓冲一起计算，均在各自预算内。CPU 有效包载荷约 55.87 MiB，两档预算都能预载，因此本图库没有单独验证提高特征缓存容量的收益。默认/小预算的源特征读取均为 0，CPU 大样本缓存访问命中计数均为 19,926,368；GPU 全库包命中 45,625 条。按需读取和淘汰通过小容量回归覆盖。

增加内存的收益取决于任务：CUDA 大样本明显受益，短 PNG 样本的小预算反而更快。本轮没有优化 PNG 编码，也不把所有场景都描述为提速。CPU 大样本相对基线小幅回退，主要收益是紧凑结果和有界匹配减少内存增长。上述数字仅代表本机固定样本。

首次串行大批次实现 `46cc598` 的 CUDA 大样本回退约 6.1%，只恢复内部 256 张提取粒度的 `cb4d628` 仍回退约 13.2%，均未满足验收。最终在预算内加入一批预取，并重新对全部五种场景预热、交替采样三次；没有用失败轮次与最终轮次混算中位数。

## 正确性与已知验收限制

| 项目 | 结果 |
|---|---|
| CPU-only / CUDA CTest | 均为 49 个核心、18 个服务回归用例；CTest 2/2 通过 |
| Web UI/API smoke | 两种构建均通过，API 2.0 及原生产参数保持不变 |
| 常规逐块索引、输出 SHA256、解码像素 | CPU/CUDA 各自的基线、小预算、默认方案一致；覆盖 1,600 块边界、分析、自适应、补齐、缺失特征 |
| 固定随机种子 Top-N=3 | 1 块 / 3 块批次的索引与像素一致；各后端单独比较 |
| 无候选 | 首批无候选继续处理后续批次，全程无候选明确失败 |
| 缓存会话 | 预载与按需读取相同，LRU 淘汰、中文路径、旧包、损坏/截断和源变化回退通过 |
| 发布/追加/恢复 | 发布失败保留旧代次，无新增追加不改有效缓存，追加、重复图片、同目录建库和重编号恢复通过 |
| 异步准备生命周期 | 拒绝重叠提交同一个池，错误在等待时传播，池可继续复用；错误退出先等待预取再释放数据 |
| CPU 160,000 块 | 逐块索引、输出 SHA256 与解码像素一致 |
| CUDA 160,000 块严格一致 | **未完全通过**：基线自身存在近似同分选图波动，见下文 |
| 显式预算采样脚本 | 小样本两档预算、四次运行 smoke 通过，输出哈希相同 |

CUDA 大样本出现两种输出，基线同一二进制重复运行也产生这两种 SHA256。索引复核的差异为 5 块：`42823、42824、42840、43624、43625`，共 2,788 个解码像素变化，最大通道差 239。常规样本全部精确一致；大样本不能据此宣称逐字节验收通过。

使用未经修改的基线 CUDA 内核，对包含第 42,823 块的同一 256 张批次重复提取 100 次，并固定之前的选图历史、候选和邻域规则。该块 L 值在 `35.107219696044922` 与 `35.107223510742188` 间变化；图库索引 12 / 40 的总分约 `540.2077028`，分差可小至十亿分之几，胜者在重复计算中翻转。这与现有 Grid LAB 的浮点 `atomicAdd` 累加顺序相符，后续四块受到邻域状态影响。原始分数和索引摘要已写入 JSON。

本轮保留原内核、公式及 `<` 平分比较，没有通过增加容差或改为确定性归约改变选图规则。要保证此类临界样本完全确定，需要单独评估 CUDA 累加或近似平分规则的调整。CUDA 分析报告中的微小浮点差异同样不能作为逐字节回归标准；固定输入张量的 CUDA 评分在不同内部分批下完全相同。

## 测量条件与计时

- 基线为 `dbb5b94` 的独立 CPU/CUDA 二进制。显式 C++ 匹配基准复用 API 解析器，未增加生产参数；基线匹配计算代码没有修改。
- Windows 10 19045 x64、Ryzen 9 7940H、RTX 4060 Laptop、驱动 616.92、CUDA 13.3.33、Visual Studio 18 2026 Release，可见内存约 31.22 GiB。
- 私有图库快照为 45,625 张、180×320 特征。每次恢复相同数据库及使用计数；目标固定为 `test_input_photos/target5.png`，`topNrandom=1`，颜色调整和分析关闭。图片/独立特征使用硬链接，缓存、ANN 和数据库位于私有目录。
- 每个版本每个场景预热一次，再轮换版本顺序各采样三次，取墙钟中位数。主机峰值取正式三次运行中最大的 Windows `PeakWorkingSetSize`，每 25 ms 查询一次；不含显存。
- 常规样本缩放目标至 360×640，9×16 输入小块，180×320 输出小块，共 1,600 块，输出 7200×12800。
- 大样本目标为 3600×6400，9×16 输入小块，18×32 输出小块，共 **160,000 块**，7200×12800 流式 PNG。

`Matching wall` 是新版从 ANN 准备到匹配资源释放的墙钟时间，包含 CPU 包预载与来源验证。图库加载/上传属于准备阶段，输出属于贴图/编码阶段。基线没有该完整字段，保留其分项原值。CPU 算子耗时和输出加载是工作线程时间之和；评分、邻域和排序有父子关系，CUDA 预取与选图、输出生产与编码存在重叠，不能将所有阶段直接相加。

`Feature source reads` 统计 TinyImage/LBP 独立文件的读取尝试，不含包文件读取或属性查询；GPU 全库读取另列 `Library feature source reads` 和包命中。图片源解码通过 `Image decodes` 统计。CPU cache hits 包含批次准备及候选访问，不能与 GPU 整库包命中当作相同分母的命中率。

## 复测入口

```powershell
cmake --build build --config Release --target mosaicraft_match_benchmark
cmake --build build_nocuda --config Release --target mosaicraft_match_benchmark
python scripts/benchmark_bounded.py --exe build/Release/bin/mosaicraft_match_benchmark.exe --baseline-exe baseline/mosaicraft_match_benchmark.exe --snapshot private/snapshot.db --request private/request.json --output-dir build/bounded-benchmark
```

`request.json` 使用 API 的字段名。例如大样本：

```json
{
  "inputPath": "D:/private/target5.png",
  "format": "png",
  "writeMode": "stream",
  "useGpu": true,
  "outW": 3600,
  "outH": 6400,
  "tileW": 9,
  "tileH": 16,
  "nativeTileW": 18,
  "nativeTileH": 32
}
```

脚本补入每轮的数据库与输出路径，固定 `topNrandom=1`、关闭颜色调整和分析，依次比较基线、`small` 和默认预算。CPU-only 的请求使用 `useGpu=false`。只运行 C++ 基准时，`small` 表示原预算；`indices`/`small-indices` 额外保存库索引二进制，供正确性检查，不用于正式耗时采样。

```powershell
ctest --test-dir build -C Release --output-on-failure
ctest --test-dir build_nocuda -C Release --output-on-failure
cmake --build build --config Release --target mosaicraft_webui_smoke
cmake --build build_nocuda --config Release --target mosaicraft_webui_smoke
```

运行验收范围为 Windows CPU/CUDA，未进行 Linux 实机验收。运行中取消、分析数据落盘和 PNG 编码优化留待后续更新。本轮不以降低峰值内存 30% 为验收条件。
